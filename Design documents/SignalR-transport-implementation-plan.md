- There is no back-pressure/coalescing in the plain-`EventHandler<T>` event model — correctness of don't raise redundant/stale events" rests entirely on `TelescopeSession`'s ingestion logic, not on the transport. "Prefer SignalR, fall back to REST" is not enough — the plan must state where the de-duplication/ordering responsibility lives and what the ordering key is.

- Resolution — STAGE 4 COMPLETE (per Get Well Guidance.md): closed. The concern above assumed a scenario — "both sources active"/"REST polling and SignalR updates are active for the same instance" — that Decision B/D (Stage 2) and Decision C (Stage 3) confirm never actually arises: for a GreenSwampClass session, SignalR and the fallback REST/AP loop are never concurrent active sources (see Decision D's Stage 4 resolution below), so there is no dual-source event storm to de-duplicate/order against a monotonic sequence or ingestion timestamp — the case this finding worried about does not occur. PART B — SCOPE AND DESIGN INTENT (reconfirmed against source docs)
====================================================================
- Two telescope classes, one contract:
  1) GreenSwamp-class telescopes: Alpaca REST for connection/commands (already built, and retained as the connection/command path regardless of SignalR state); telescope **state** is sourced from the GreenSwamp SignalR channel (`TelescopeStateHub`) as the **single source of truth for all state fields** while the SignalR connection is healthy (Decision B/D, Stage 2 of Get Well Guidance.md) — superseding this document's earlier "supplementary, opportunistic" framing (architecture §6.4, requirements FR11/FR13) for the state-telemetry path specifically. REST/AP state polling is used only as a fallback after irrecoverable SignalR loss (Decision D).
  2) Standard Alpaca-class telescopes: Alpaca REST/`DeviceState`/other `ITelescopeV3`/`ITelescopeV4` properties only — never attempts a SignalR connection (requirements FR13, Definitions "GreenSwamp-class device"). Fields absent from `DeviceState` (`TargetRightAscension`, `TargetDeclination`, `SiteLatitude`, `SiteLongitude`, `SiteElevation`, `AlignmentMode`) are populated via individual Alpaca property (AP) requests on the cadences fixed by Decision B (Stage 2).
- `ITelescopeSession` is the stable seam (already built): `ConnectAsync`, `DisconnectAsync`, `FindHome`, `ParkAsync`, `AbortSlewAsync`, `StateUpdated`, `ConnectionStatusChanged`, `Capabilities`, `Status`. This plan adds no new members to that public interface — the SignalR path is purely an additional internal data source feeding the same `StateUpdated` event (architecture §6.2/§6.5/§6.6).
- ViewModel/UI must remain fully transport-agnostic — no `Microsoft.AspNetCore.SignalR.Client` orASCOM type ever crosses into `GreenSwamp.Alpaca.Client.ViewModels` or the Avalonia app project (architecture §4 layering rules, already enforced by project references today).

PART C — DECISIONS REQUIRED BEFORE IMPLEMENTATION STARTS (for your review)

Decision A — RESOLVED (Stage 1, per Get Well Guidance.md): fix `IsGreenSwampClass` detection now, as Phase 0 work.
- Confirmed mechanism: detection uses the ASCOM Alpaca `DriverInfo` string only — no `Description` matching, and no server-level `management/v1/description` probe. The reference server's `DriverInfo` is derived directly from the server build assemblies in the standard .NET assembly-identity format `"GreenSwamp.Alpaca.Server, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null"`. The client recognition check must: (1) split `DriverInfo` on commas, (2) compare the first field, trimmed, against the known name `"GreenSwamp.Alpaca.Server"`, and (3) confirm a `Version=` field is present and its value is a valid four-part version string in the format `a.b.c.d` (which may legitimately be `0.0.0.0`). Both (2) and (3) must pass together — the version check guards against a coincidental name match on an unrelated/malformed `DriverInfo` string. This supersedes the previous three-hard-coded-marker/`Description`-based approach and the previously-recommended `management/v1/description` probe.

Decision B — RESOLVED (Stage 2, per Get Well Guidance.md): field placement/sourcing is per-class, not a single shared placement.
- Confirmed model: `TargetRightAscension`, `TargetDeclination`, `SiteLatitude`, `SiteLongitude`, `SiteElevation`, and `AlignmentMode` are **not** DeviceState fields for either class (confirmed absent from design §4.1's DS table) — each class sources them differently:
  - **AlpacaClass**: sourced via individual Alpaca property (AP) requests, on two fixed cadences — `AlignmentMode`/`SiteLatitude`/`SiteLongitude`/`SiteElevation` are queried once at session start and every 30 seconds thereafter (these change rarely/never during a session); `TargetRightAscension`/`TargetDeclination` are queried on every `Slewing` false→true transition and every 1 second thereafter (these are only meaningful/changing during an active slew-to-target). These AP results are used to update the neutral `TelescopeState` fields — the same neutral type both classes populate.
  - **GreenSwampClass**: sourced exclusively from the SignalR-communicated telescope state, as part of the "single source of truth for all fields" rule (Decision D) — not via the AlpacaClass AP-polling cadences above, and not placed on a GreenSwamp-only extension type. AP/REST values for these fields are used only as the Decision D fallback after irrecoverable SignalR loss, at which point the AlpacaClass cadences above are the fallback polling behavior.
- This supersedes both this plan's original recommendation (single shared placement on neutral `TelescopeState`, populated identically for both classes via AP) and the SignalR spec's original placement (all five fields as `GreenSwampTelescopeState`-only additions) — neither of those two positions is what Stage 2 confirms. The fields live conceptually on the neutral `TelescopeState` (both classes' ViewModels bind to the same properties), but the *sourcing mechanism and update cadence* differ fundamentally per class, which is the actual substance of this decision.
- Open discrepancy carried forward (not resolved by this stage, see A2/A11): (a) `TrackingRate` was in this plan's original five-field list but is not named in the Stage 2 guidance text — whether it follows the GreenSwampClass single-source-of-truth rule like the other fields, or remains AP-only/polled, is unresolved; (b) `SiteLongitude`/`SiteElevation` have no SignalR spec field to source from at all yet (A11) — the GreenSwampClass "single source of truth" rule cannot be implemented for these two fields until the spec/server add them.
- **Both discrepancies now RESOLVED (end-of-stages clean-up, see Finding A2/A11 above):** `TrackingRate` follows the same per-class sourcing model as the other five fields — neutral `TelescopeState` placement, SignalR sole-source-of-truth for GreenSwampClass while connected, AP-fallback on the 30-second site/alignment cadence. `SiteLongitude`/`SiteElevation` are confirmed for addition to the SignalR spec (`greenswamp-telescopestate-signalr-spec.md` §11.4/§11.5) and follow the same per-class sourcing model once the server-side field addition lands. All six fields named in this decision are now on a single, consistent per-class sourcing model with no remaining placement ambiguity.

Decision C — RESOLVED (Stage 3, per Get Well Guidance.md): a poll loop is required for both GreenSwampClass and AlpacaClass telescopes, at two fixed top-level cadences.
- Recommendation (superseded — retained for traceability): build a minimal `TimeProvider`-driven REST poll loop as part of Phase 2 of this plan, scoped narrowly (just "publish `StateUpdated` on a timer while connected," reusing the existing `AlpacaTelescopeProvider.GetState`) — because `TelescopeSession`'s reconciliation logic (Decision D) is meaningless without a second, ongoing REST-sourced stream to reconcile against. Doing this as a drive-by inside the SignalR work is more coherent than reconciling "SignalR live data" against "REST data that only exists at connect time and after commands."
- PARTIALLY RESOLVED (Stage 2, per Get Well Guidance.md): the field-level polling *cadences* the loop must implement for AlpacaClass telescopes are now fixed by Decision B — a single generic "poll `DeviceState` on a timer" loop is not sufficient on its own; the loop must also drive two additional, independently-timed AP-polling schedules: (1) `AlignmentMode`/`SiteLatitude`/`SiteLongitude`/`SiteElevation` at connect and every 30s, and (2) `TargetRightAscension`/`TargetDeclination` on `Slewing` false→true transition and every 1s. The loop's internal implementation mechanics (timer composition, whether these are one loop with sub-cadences or several independent timers, how the 1s target-coordinate polling starts/stops around the slewing-transition trigger) are **not** decided by this stage — tracked as Stage 3 ("Poll loop") of Get Well Guidance.md, not resolved here.
- RESOLVED (Stage 3, per Get Well Guidance.md): a poll loop **is** required for both classes — this confirms A3's gap must be closed, not descoped. Two top-level cadences are fixed:
  - **SignalR loop, 250ms cadence** — GreenSwampClass telescopes only, while the SignalR connection is healthy. This is the loop that ingests each `ReceiveTelescopeState` push and republishes `StateUpdated` from it; 250ms matches the reference server's own internal `TelescopeStateService` tick (already noted as an informal default in architecture §6.3) and is now a confirmed requirement, not a "reasonable starting point."
  - **ASCOM Alpaca `DeviceState` loop, 1 second cadence** — for AlpacaClass telescopes, this is the primary and only continuous state-polling loop (re-polling `DeviceState` every second for the duration of the session). For GreenSwampClass telescopes, this same 1-second `DeviceState` loop is the Decision D **fallback** loop only — it does not run continuously alongside the SignalR loop; it engages only after irrecoverable SignalR loss (5 failed reconnects at 2/5/10/10/10s) and stops again once SignalR resumes as sole source of truth.
  - These two poll-loop cadences (250ms SignalR / 1s `DeviceState`) are **in addition to**, not a replacement for, the two AP-property cadences already fixed by Stage 2/Decision B (30s for `AlignmentMode`/`SiteLatitude`/`SiteLongitude`/`SiteElevation`; 1s + slewing-transition for `TargetRightAscension`/`TargetDeclination`) — those AP requests cover fields absent from `DeviceState` and are unaffected by this stage.
  - RESOLVED (Stage 4, per Get Well Guidance.md): the internal timing/thread-safety mechanics previously tracked here are closed. The only case of multiple concurrent cadences is for AlpacaClass telescopes (and GreenSwampClass telescopes during the Decision D fallback window): the `DeviceState` loop (1s), the site/alignment AP cadence (30s), and the target-coordinate AP cadence (1s + slewing-transition) all run for the same session. Since the cadences are fixed and well-known, these REST calls (all blocking) are time-ordered/sequenced so each field is saved into the model as its individual call completes; the standard OnChange/property-update pattern then applies per field exactly as it would for a single-cadence loop. No single shared timer/lock-based composition scheme is mandated by this stage — sequencing the calls is sufficient, and is not decided further here (an implementation-time detail, not a design gap). GreenSwampClass telescopes while SignalR-connected have only the one 250ms SignalR loop active (the 1s `DeviceState` loop is dormant), so no multi-cadence sequencing question arises for that state at all.

Decision D — Reconciliation/ordering algorithm specifics (architecture §6.5, test-strategy §12, requirements FR42/FR43), still an open item prior to this plan:
- Recommendation: attach a `TimeProvider`-derived ingestion timestamp (not either transport's own wall clock) to every snapshot at the point `TelescopeSession` receives it from either provider; when both a REST and a SignalR snapshot are available, always prefer the SignalR one if its ingestion timestamp is newer than the last value already published, and only publish a REST snapshot when no SignalR snapshot has been ingested within the poll interval (i.e. REST fills gaps, never overwrites a fresher SignalR value with a stale REST one). This is a proposal for confirmation, not yet implemented anywhere.
- CONCEPTUALLY RESOLVED for GreenSwamp-class devices (Stage 2, per Get Well Guidance.md) — this supersedes the "prefer freshest of REST+SignalR, continuously merged" model above for GreenSwampClass telescopes specifically: SignalR is the **single source of truth for all state fields** while the SignalR connection is healthy — there is no continuous freshness-based merge against REST/AP for a GreenSwampClass device. `TelescopeSession` only switches to REST/AP-sourced state for a GreenSwampClass device after an **irrecoverable** loss of the SignalR connection, defined precisely as: failure to re-establish the connection after 5 retries, at intervals of 2, 5, 10, 10, and 10 seconds. Once SignalR reconnects successfully (at any point, including after the fallback has engaged), it resumes being the sole source of truth again — the fallback is not a one-way, permanent transition for the life of the session.
  - This reconciliation model does not apply to AlpacaClass telescopes at all (they have no SignalR source to reconcile against) — their state is always AP/DeviceState-sourced per Decision B's cadences; there is no "prefer SignalR" step for that class.
  - RESOLVED (Stage 4, per Get Well Guidance.md): the cross-thread/staleness mechanics previously tracked here are closed, on two grounds. First, there is no transition-boundary staleness risk to guard against: either the SignalR connection is healthy (SignalR is the sole active source) or it has been marked failed after the 5-retry/2-5-10-10-10s schedule (the fallback loop is the sole active source instead) — the two are never concurrent active sources for the same session, so there is no parallel-source window in which a REST/AP-sourced snapshot could be treated as stale relative to a SignalR one, or vice versa. Second, "irrecoverable" does not need a bespoke cross-thread signaling mechanism: `TelescopeSession` (the telescope model) already owns all transport concerns end-to-end — regardless of which thread the retry-exhaustion determination happens on (the SignalR client's own reconnect handling, a timer callback, or elsewhere), it is `TelescopeSession` itself that decides source/validity, so "which thread learned about the failure first" is not a design problem requiring a separate solution. The exact mechanics of counting the 5 retries against `WithAutomaticReconnect()`'s own built-in behavior (vs. independent tracking) remain an implementation-time detail, not a design gap requiring further resolution.
